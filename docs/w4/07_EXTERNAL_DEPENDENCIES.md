# W4-07 外部依赖、授权与风险跟踪

## 1. Canvas Developer Key
**优先级：最高优先级并行外部任务。**

### 当前方案
- Canvas 实例地址由用户配置。
- 个人 API Token 仅用于开发者本人本地验证。
- 不共享个人 Token，不上传 Supabase，不写 GitHub，不传给 AI。
- 五人多用户接入目标采用 OAuth；需要学校/Canvas 管理员创建 Developer Key，并确认只读 Scope、Redirect URI、授权政策和 Token 生命周期。
- Canvas Adapter 从第一天区分 PersonalTokenProvider 与 OAuthProvider，共用课程/作业业务接口。

### 申请材料
- 项目名称和用途：Agent-to-Entrepreneurship，学生个人学习与任务管理。
- 使用场景：读取经用户授权的课程、作业、截止时间及允许访问的日历事件。
- 用户范围：五人内部测试，后续是否公开另行申请。
- 权限原则：最小只读 Scope；不写成绩、不代交作业、不更改课程数据。
- 数据处理：按用户隔离，个人课程数据不默认共享团队。
- 安全措施：OAuth 独立授权、系统安全存储、撤权、数据最小化。
- 技术材料：Canvas 实例 URL、OAuth Redirect URI、请求 Scope、测试账号计划和应用联系人。

### 申请与验收记录
在团队内部安全的项目管理位置记录申请日期、联系对象/角色、反馈、审批状态和下一步。公开仓库只记录非敏感状态，不写 Client Secret、Token 或个人身份信息。

### 风险处理
- Developer Key 未获批：继续开发者本人 Token 的本地真实读取，但将 OAuth/五人独立授权标记阻塞；不能共享个人 Token。
- 管理员不允许所需 Scope：记录缺失权限，向用户说明影响，不能绕过平台政策。
- OAuth Secret 需要保密交换：不得打包进 Electron 客户端；按 W3 设计使用适当安全授权交换/服务端组件。
- 用户撤权：立即停止后续同步并使本地凭据失效。

## 2. 上海交通大学邮箱
### 公开配置参考
- IMAP：mail.sjtu.edu.cn，端口 993。
- SMTP：mail.sjtu.edu.cn，端口 465。
- 以上是官方公开接入资料给出的候选配置；真实客户端认证方式、应用专用凭据、账号策略和发送限制必须使用获准测试账户验证，不能假定普通 jAccount 密码一定可用。

官方参考：
- https://net.sjtu.edu.cn/wlfw/dzyj.htm
- https://net.sjtu.edu.cn/info/1191/2699.htm
- https://developer.sjtu.edu.cn/api/mail.html

### 验证清单
- 是否允许第三方 IMAP/SMTP 客户端。
- 需要何种密码/授权凭据/OAuth。
- TLS/SSL 模式和证书验证。
- 收件箱分页、增量同步和已读状态。
- SMTP 发件人限制、每日限额、附件大小。
- 测试邮件能否到达指定收件端。
- 断网/超时后如何核验发送状态。

不得通过关闭 TLS 证书验证、硬编码密码或绕过学校策略来获得“连接成功”。

## 3. Supabase 最小技术验证
Supabase 是方案 C 中优先验证的候选，不是已最终选定的正式后端。

PoC 必须验证：
1. 五个独立用户账号可注册/登录。
2. 五人加入同一 Workspace。
3. 非成员无法读取/修改 Workspace 记录。
4. 共享任务更新可实时到达其他账号。
5. 消息可跨设备实时显示。
6. 断网重连后状态可核对，不静默丢失。
7. 密钥分为公开客户端配置和仅服务端保密 Secret；Service Role Key 绝不能进入桌面包。
8. 服务区域、免费/付费配额、备份和数据删除要求适合团队测试。

通过后才确定用于 Alpha；不通过则比较替代方案并记录成本和开发影响。参考：https://supabase.com/docs

## 4. AI Provider
- 使用真实模型前明确每位用户的 API Key 或统一服务账号模式；不得把 ChatGPT 订阅当作 API 额度。
- API Key 使用系统安全存储或合适的服务端密钥管理，不写入仓库、普通日志或团队共享表。
- 云端模型读取个人邮件/知识文档前明确独立外传授权。
- 记录调用失败、限额、费用提示和可替换 Provider。
- Alpha 不要求自主 Agent 获得高风险写入权限。

## 5. Windows/macOS 设备与发布依赖
需要确认可用于真实测试的 Windows 设备、Mac 设备、系统版本和芯片架构。两种系统都要完成安装/启动和核心 E2E。内部 Alpha 不要求应用商店上架；签名、公证和公开自动更新按正式发布门槛处理。不得把另一系统的测试结果推定为通过。
