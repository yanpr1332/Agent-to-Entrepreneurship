# W4 开发计划与验收体系

> 基线日期：2026-11-07；内部原型目标：2026-11-25。W4 计划已获用户确认并进入 PR 审阅；W5 代码开发尚未启动或获授权。

## W4 目标
把 W1 PRD、W2 UI/UX 和 W3 技术架构转化为可执行的内部 Alpha 开发计划。团队为五名学生，开发时间受学业约束，主要采用 AI 辅助编程；不假设每人具备完整软件工程经验，也不把固定岗位或固定任务永久绑定到某个成员。

11 月 25 日目标是一个 Windows/macOS 均可运行、五名成员可通过互联网进入同一云端工作空间、能够操作八大模块基础闭环的内部原型。它不是应用商店版本，也不是完整正式产品发布。

## 关键约束与决策
| 编号 | 已确认决策 |
|---|---|
| W4-DEC-01 | 五名学生组成团队，AI 辅助主要代码生产；质量与速度平衡；任务按工作域和能力动态认领，不预先固定到个人 |
| W4-DEC-02 | Windows 与 macOS 混合；互联网云端共享工作空间；两种系统都必须用于原型演示和测试 |
| W4-DEC-03 | 云端采用方案 C：先做最小验证，再决定是否使用 Supabase；Supabase 是候选，不是已锁定的正式架构 |
| W4-DEC-04 | Canvas 支持用户配置实例地址，认证支持 Token 与 OAuth；Token 仅用于开发者本人本地验证，优先推进 OAuth；邮件首版采用通用 IMAP/SMTP，优先保证交大邮箱 |
| W4-DEC-05 | 联系老师/学校管理员申请 Canvas Developer Key 是最高优先级并行任务；个人 Token 不得共享给其他成员 |

## 重要范围说明
1. PRD 中八大模块的正式 P0/P1/P2 划分保持不变。本次内部 Alpha 是限期原型，不得把尚未实现的正式 P0 私自改成 P1。
2. Canvas 真实连接和交大邮箱真实收发是本次原型明确必交付项；模拟连接、静态数据或“看起来已连接”不能通过验收。
3. Canvas 个人 Token 只用于开发者本人的本机验证；五人多用户 OAuth 依赖学校/Canvas 管理员批准 Developer Key。申请工作立即并行推进。
4. 邮件读取、AI 分析、写草稿和发送是不同权限。真实发送必须由用户逐次确认。
5. 五人云端协作必须使用独立账号和服务端权限规则；不以同一账号、局域网共享或本地模拟数据代替。
6. Supabase 先验证后选定。通过验证不等于正式产品已完成完整云同步。
7. 11 月 25 日不要求应用商店上架或正式签名发布，但要求 Windows/macOS 测试设备均可安装/启动，并有内部测试说明。
8. 本次归档只写规划、任务、流程和验收文档，不初始化应用工程、不安装依赖、不部署云服务、不配置真实密钥、不启动 W5。

## 进度口径
每项任务使用：待开始、进行中、待验收、已通过、阻塞、明确不纳入本轮。只有提供代码/构建/测试证据并完成复核后才能标记“已通过”。计划文档归档不等于任务实现或测试通过。
