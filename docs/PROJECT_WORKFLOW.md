# 下一阶段工作流程与协作约定

> 状态：W1 PRD 已归档；W2 交互与 HTML 原型已归档、最终体验签收待完成；W3 架构已归档；W4 开发计划已确认并进入独立 PR；W5 代码开发尚未启动，也未获授权。

## 总体顺序

1. **完善 PRD V1.0**：将八大模块逐一细化为可开发、可验收的功能需求。
2. **设计 UI/UX**：确定信息架构、页面、导航和交互流程，制作并评审界面原型。
3. **完善技术架构**：明确模块接口、数据模型、数据库和 Windows/macOS 的适配边界。
4. **制定开发计划**：形成按模块和阶段拆分的开发任务、里程碑与验收清单。
5. **正式启动第一轮开发**：在前四步审议完成并获得明确许可后开始实现。

按顺序推进；必要时可以在讨论中往返修改，但不能把尚未确认的建议自动当成最终决策。

## W1 — 详细 PRD V1.0

**目标**：把目前的 PRD V0.1 从功能概要细化为开发团队可以直接理解和验收的需求。

- 覆盖八大一级模块：①日历与任务；②个人知识库；③专注与自律；④小组协作；⑤AI 智能规划；⑥数据接入与扩展；⑦邮件管理与 AI 通信；⑧个人工作台。
- 为每个功能建立编号、使用者、使用场景、前置条件、触发方式和正常/异常流程。
- 分别明确**输入、处理规则、输出及状态变化**；注明与其他模块的数据关系。
- 标注 P0（MVP）、P1（增强）、P2（远期），并写明选择该优先级的理由和依赖关系。
- 给出可复核的验收标准，包括错误提示、空数据、离线、权限、安全和跨平台行为。
- 明确需要用户决策的歧义和开放问题，记录定稿版本。

**交付物（已形成）**：[详细 PRD V1.0](PRD.md)，含功能编号、优先级、输入输出、主要用户流程、权限边界和端到端验收矩阵。性能量化门槛、真实平台授权、详细角色矩阵仍留 W3/W4 验证。

**完成门槛**：八大模块均有功能级需求；跨模块职责不冲突；P0 的验收条件可执行；用户审阅并确认。

## W2 — UI/UX 与界面原型

**目标**：让用户在编码前确认产品的操作体验。

- 确定整体信息架构、主导航/次级导航和跨模块跳转。
- 列出首页、日历、任务、知识库、专注、协作、AI、邮件、连接器和设置等主要页面及其层级。
- 设计首次启动、账号/学校平台接入、创建任务、导入资料、专注执行、邮件审核发送、团队认领等关键流程。
- 制作线框图和可演示原型；提供备选布局供用户选择、调整。
- 设计空状态、加载、失败、撤销、权限确认、通知及无障碍/键盘操作。
- 确保 Windows/macOS 视觉和交互体验一致，同时尊重系统差异。

**交付物（已归档待最终体验签收）**： [W2 UI/UX 文档总览](ui-ux/README.md)、[信息架构及页面树](ui-ux/01_IA_AND_PAGES.md)、[逐条交互规范](ui-ux/02_INTERACTION_DECISIONS.md)、[关键用户旅程](ui-ux/03_MODULE_JOURNEYS.md)、[状态/权限规范](ui-ux/04_STATES_AND_PERMISSIONS.md)、[W2 验收与未决清单](ui-ux/05_W2_ACCEPTANCE.md)，以及 [可点击 HTML 原型](../prototypes/w2-hybrid-workspace/index.html)。

**完成门槛**：主要 P0 场景可用原型走通；用户审阅并确认总体布局与交互方向。

## W3 — 技术架构与详细接口

**目标**：将需求与界面映射到清晰、可维护的实现结构。

- 确定模块边界、依赖规则、共享领域模型和数据流。
- 设计任务/事件、课程、知识资料、专注记录、协作项目、邮箱邮件与草稿等数据库实体及关联。
- 定义模块内部接口、连接器接口、同步/离线冲突处理、权限和审计机制。
- 细化 Canvas、上海交大官方 API、邮件服务、Obsidian、ASR 和 AI 模型接入边界。
- 单独明确 Windows/macOS 原生适配层、构建目标及专注限制功能的安全降级方案。
- 记录技术选型、取舍和仍需验证的风险；此阶段为设计，不自动启动编码。

**交付物（待制作）**：架构设计文档、模块接口规范、数据库 ER 模型、跨平台适配矩阵、关键架构决策记录。

**完成门槛**：P0 功能均能对应到负责模块、数据与接口；关键安全约束明确；用户审阅并确认。

## W4 — 开发计划与验收体系（2026-11-07）

**目标**：将 W1/W2/W3 转化为可在 2026-11-25 前交付的 Windows/macOS 内部 Alpha 任务计划，同时保留正式 PRD P0 范围。

- 团队为五名学生，时间受学业约束，AI 辅助承担主要代码生产；不固定将五人永久绑定到五个岗位。
- 任务按责任域和当周时间动态认领；每项任务记录临时 Driver、Reviewer、修改范围、依赖、验收人和证据，防止重复与冲突。
- Alpha 必须有八大模块基础可操作闭环；Canvas 真实读取和交大邮箱真实收发是明确必交付项。
- Canvas 个人 Token 只用于开发者本人本地验证；联系老师/管理员申请 Developer Key 是最高优先级并行任务，OAuth 用于五人独立授权目标。
- 邮件采用通用 IMAP/SMTP，优先保证交大邮箱；邮件读取、AI 分析、草稿和真实发送分权，发送逐次确认。
- 云端方案采用 C：先验证 Supabase 的五人账号、Workspace、RLS、Realtime 和断网恢复，再决定是否用于 Alpha。
- Windows/macOS 均须实际启动和核心流程验收；内部 Alpha 不要求应用商店上架。
- W4 任务、责任边界、AI 编程、验收、里程碑和外部依赖见 [W4 总览](w4/README.md)。

**完成门槛**：W4 文档和任务索引完整，用户确认范围和日期；本次 PR 仅归档规划，不等于 W5 已授权。

## W5 — 第一轮正式开发

**启动条件**：W1–W4 所需决策已经确认，并且用户明确授权开始写代码/仓库。

- 初始化约定的代码工程、规范和双平台构建/CI 基础设施。
- 按批准的第一轮任务清单开发、测试、修复、审查并提交。
- 严格区分“已实现”“已测试”“尚待真实设备验证”，不得虚报完成状态。
- 对高风险能力（如程序锁闭、邮件发送、团队权限）遵守安全发布门槛。

**交付物（待制作）**：第一轮可运行代码、测试结果、变更记录、验收清单。

## 协作和仓库写入约定

1. 后续以**讨论驱动**：助手可以提问，也可以提出多个备选方案；用户选择、调整、补充后逐项定稿。
2. 讨论中的草案和用户选择先在对话内确认；**未经用户明确许可，不对 GitHub 仓库进行新增、修改、提交、分支创建或其他写操作**。
3. 用户明确批准一次仓库写入时，权限仅覆盖该次说明的范围；不自动授权后续阶段提交。
4. 完成每项工作后列出确认结果、尚有争议的点与建议的下一项讨论，不擅自跳到下一个开发阶段。
5. 需求发生调整时，先说明对其他模块、UI、接口、开发计划的影响，再决定是否更新相关文档。
