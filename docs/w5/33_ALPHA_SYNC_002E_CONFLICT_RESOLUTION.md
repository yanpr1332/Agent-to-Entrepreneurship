# ALPHA-SYNC-002E：冲突解决安全闭环（第一部分）

> **状态：代码/自动化验证阶段。** PR #38 已合并；本轮只实现可安全裁决的“本地未上传修改 vs 云端更新/删除”冲突。不部署 Supabase、不做生产数据库迁移、不启用自动后台同步，也不声称真实多设备同步已验收。

## 目标及明确边界

- **保留本机**：用户先比较双方快照，二次确认后，使用所审阅的云端版本作为新的 baseVersion，并轮换 operationId；此时本机仍未上传，必须再次点击“立即同步”。若服务端在确认后继续变化，版本 CAS 会拒绝后续上传，而不是静默覆盖。
- **采用云端**：用户明确二次确认后，取消当前账号对应实体的 pending，用所审阅的远端快照更新本机任务或手动课程。对云端删除的确认属于真实本地删除，提示不可在本界面撤销。若本机其他云账号还关联同一实体则拒绝此项，以免一个账号覆写另一账号数据。
- 不会自动裁决来源不合格的实体、与已确认学习计划重叠的课程、日历容量问题；不得删除 Canvas/ICS/邮件候选。
- 冲突记录存在时，后续手动同步**跳过该实体的 push**；增量拉取只刷新此冲突的远端版本和快照，不自动将其内容写入本地实体。
- IPC 只接受实体类型、实体 UUID、已审阅远端版本、已审阅本地 operationId、动作；**账号 ID、设备 ID、游标、payload 都不得从 Renderer 传入**，当前身份始终由 Main 中云端认证会话取得。
- 点击最终确认时，Main 先进行一次手动同步、拉取最新分页；若还有未拉完的远端页面则拒绝本次裁决。之后同步执行版本/本地操作 CAS。任何在用户审阅后发生的版本变化都会要求刷新重新审阅。
- 此阶段不提供“强制忽略安全冲突”的按钮。

## 失败/断网的行为

- 若冲突存在，断网时不能以旧远端快照强制“采用云端”；仍可查看冲突，联网后再提交。
- 更新后的本机待发送意图使用新的 UUID，不复用已经发生过服务端冲突的原 operationId。
- Main/Renderer 并发同步时禁止进行裁决，避免重基与旧 HTTP 回执竞态。
- 对手动日历先在 calendar SQLite 事务中处理，再清除 local SQLite 的冲突记录；跨库不能组成一个真正的原子事务。若进程恰好在两库提交之间崩溃，冲突记录仍保留作为恢复线索，而不会假装已解决。完整恢复/重放流程仍是下一项工作。
- 用户在冲突产生之后修改了本地条目、撤销授权或切换账号，旧本地 operationId 不匹配时必须刷新复核，绝不盲目使用旧选择。

## 本地测试

仓库根目录、Node 24.x、npm 11.x：

```sh
npm ci
npm run typecheck
node node_modules/vitest/vitest.mjs run src/main/personal-sync.test.ts src/main/local-store.test.ts src/main/fixed-calendar-store.test.ts src/shared/personal-sync-contract.test.ts src/shared/ipc-channels.test.ts
npm test
npm run build
```

在独立测试数据目录启动 Electron 时，逐条检查：A/B 双方标题、截止日期或课程时段均可见；点击一个决策后必须二次确认；“采用云端”只改变该条目；“保留本机”会提示再手动上传；旧版本或已修改过的本机操作必须拒绝；确认“采用远端删除”前展示警告。自动化使用 Mock 云端，不能证明 Supabase RLS 或网络真实一致。
